## 1. 结论

- R2-D 只收口刚哥指定的核心：执行中给一两句人话摘要；任务结束时，不论工具成功、空结果、拒绝、失败或结果未知，都让同一个小伴模型依据真实 ToolResult 生成总结性答卷。
- 最终答卷不是代码拼出的状态句，也不是系统回执。它要求说明做了什么、实际结果、未完成项及具体原因，并在有用时给出下一步；Node 和网页原样放行这份 `agent-reply`，只显示一次。
- 本轮没有新建 loop、SSE、回复出口、验收框架或业务分支。R2-D 唯一生产代码增量是强化现有 strict final slot 的模型指令；其余为现有链路上的定向验收样例。

## 2. 实际机制

- 连续工具仍在同一模型回合内运行：模型先说当前在做什么，工具真实执行，canonical ToolResult 回到同一模型，再由模型决定继续调用下一工具或结束。
- 工具前的模型正文只在真实 tool call 已绑定并开始后投影为脱敏执行摘要；它不会混入最终答卷。摘要无法安全脱敏时，页面只显示不含参数的短句，不冒险泄露业务正文。
- 最后一轮仍调用同一个已配置模型，只关闭工具能力以避免任务结束后继续派发；模型可看到此前 ToolResult，并收到“完整总结、不要一句状态、不要模仿系统回执”的明确要求。
- 成功、空结果、拒绝、失败和 `dispatched + unknown` 均回到模型后再收尾。工具失败不会触发 Node 固定失败文案替换模型答卷。
- 只有模型服务本身在最终轮物理失败、根本没有生成答卷时，才保留独立 typed system failure；它不能伪装成小伴总结，也不会重跑已完成工具。

## 3. 核心对抗样例

- 两个连续工具：顺序严格为“摘要一 → 工具一 → 摘要二 → 工具二 → 唯一完整答卷”；两个工具各执行一次。
- 五类 ToolResult：`success / empty / denied / failed / unknown` 全部进入同一模型的下一轮，最终均为至少两句的自然总结，且失败原因和可继续位置没有被吞掉。
- Gateway 同一轮同时含一个成功工具和一个拒绝工具时，完整模型总结仍穿过 SSE；工具前铺垫被移出最终正文，最终正文只出现一次。
- Node 收到 `not_found` 工具结果后的模型总结时，持久化为 `agent-reply`，明确不得改写成“系统记录的原因”。
- 大 ToolResult 触发压缩后，工具不重复执行，压缩后的同一回合仍能形成最终答卷。
- 最终模型调用物理失败时，已成功的工具步骤保留一次且不重派发；公开结果为 typed provider failure，不伪造模型口吻。
