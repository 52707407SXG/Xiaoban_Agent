## 3. 唯一结果

### 3.1 真实时间线

- 网页严格按服务端事件原顺序展示 request、turn、tool 与 control；不再按前端时间猜测重排。
- 执行中和失败时间线保持展开；成功时间线自动折叠且可重新打开。
- 每个事件独立显示动作、脱敏摘要和状态；最终答卷只在 transcript 出现一次，不复制到时间线。
- 刷新、SSE 重连、重复终态帧和旧版本快照不能重复正文或 ACK。

### 3.2 授权与内容补充

- 审批胶囊只提供四个明确动作：`单次授权 / 会话授权 / 内容补充 / 拒绝`，支持键盘左右移动但不抢原输入框或 IME 焦点。
- 内容补充复用原有 textarea，不创建第二输入器、不新增普通用户气泡、不写 localStorage/sessionStorage；公开面只保留 SHA-256 digest 和固定摘要。
- 每个控制绑定 `deliveryId + approvalId + controlId`；内容补充再绑定规范化正文 digest。combined steer 精确绑定所选 approval/turn/call，其他 call 的 pending 可独立保留，同一 call 多 pending 时 fail closed；standalone steer 只允许零 pending 且恰好一个 open tool。
- 每个 delivery 最多 8 个唯一 control，pending 也预占容量；第九个新 control 拒绝，既有精确回执仍可重放。

### 3.3 HTTP、SSE、重启与停止竞态

- Agent HTTP 返回 accepted 之后，Node handler 必须等到同一 control 的精确 SSE 回执已经进入 DeliveryStore 才返回 202；等待窗口内未看到回执则返回 503 ambiguous，不伪造成功。
- 进程重启后按 `control → tool → turn → request` 恢复；已经耐久化的 control 可精确重放，不再次调用 Agent。
- 网页遇到 0/408/5xx 时保留原 controlId 和原选择/原文，只用精确 receipt 消歧；歧义期间改选或改文不能生成第二个 control。晚到的精确 receipt 可正常结算，正文只在仍等于原补充时清空。
- 停止操作绑定用户实际看到的 deliveryId。即使服务端已从 generating 抢跑到 delivering，点击停止仍阻断最终正文和 delivery ACK；停止终态保留独立 system receipt，不伪装为小伴回复。

### 3.4 隐私边界

- 补充正文只进入当前受信模型轮次，不进入公开 progress、durable audit、浏览器存储、普通 transcript 或控制回执。
- Provider 在首 token 前、partial stream、retry、异常 body/metadata/status、request dump、stdout/stderr 中反射补充正文时均固定遮蔽；诊断 HTTP 状态只接受严格 `int 100..599`。
- 本轮只证明应用持久化、日志和标准 SDK 可达面不落补充正文；不宣称反向代理永不对 8–24KB request body 使用临时文件。

## 4. 关键对抗样例

- accepted 后 HTTP 回包丢失：网页先显示未确认，精确持久回执晚到后自动结算，不能误报失败。
- 歧义审批改选、歧义补充改文：均不生成新 POST/controlId；恢复原操作后仍使用原 controlId。
- 两个 open tool、两个不同 call 的 pending：combined steer 只关闭目标 approval，另一 call 保持 pending；同一 call 的第二 pending 则拒绝。
- U+0085 不被 ECMAScript trim 删除；FEFF/U+3000 被两端一致删除，digest 完全一致。
- control 上限、重启重放、终态 close、late SSE、重复 terminal、stop/delivering race 均有精确负例。
- 补充 canary 被 Provider 放入异常字符串、headers、status、body、response text 和截断 marker 时，日志、dump、stdout/stderr 与网页均无 canary。
